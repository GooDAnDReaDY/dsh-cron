# ADR-0001: Внешний REST API под токеном и задачи из конфига

- Статус: Accepted
- Дата: 2026-09-11
- Проект: dsh-cron
- Связанные Gitea issues / PR: #50, #54, #53, #121; PR блока 0.2.7
- Заменяет / заменён ADR: нет

## Контекст

Планировщику нужны две новые поверхности: постоянные задачи, объявляемые
оператором в конфиге профиля (cordis.patch.yml), и управление задачами из
внешних систем (CI, cron хоста, curl) без доступа к панели. Обе поверхности
создают задачи, а задача типа script/skill/workflow исполняет код. До сих пор
создание такой задачи требовало явного подтверждения (заголовок по HTTP,
confirmCodeSwitch у инструмента агента). Нельзя допустить, чтобы новая
поверхность стала обходным каналом исполнения кода, и нельзя допустить, чтобы
конфиг и UI бесконечно перетирали друг друга.

## Решение

1. **config.jobs — владелец объявленных задач.** Задача из конфига получает
   метку managedBy: config. При старте профиля объявленные задачи создаются или
   обновляются, а ранее управляемые конфигом задачи, которых в конфиге больше
   нет, удаляются. Задачи, созданные через UI, API или инструменты, конфиг не
   трогает.
2. **Управляемые задачи защищены в UI**: помечены как конфиг-задачи, действия
   правки и удаления для них недоступны с пояснением, что источник — конфиг.
3. **Токен внешнего API хранится в настройках плагина** как маскированный ключ
   (тот же режим, что botToken) и проверяется как Bearer только на новом
   префиксе /dsh-cron/api/*. Существующие маршруты панели остаются локальными и
   cross-origin-защищёнными, как сейчас. Сравнение токена — постоянное по
   времени; незаданный токен даёт 503, неверный — 401.
4. **Гейт код-исполняющих типов сохраняется на обеих новых поверхностях.**
   Внешний API требует то же подтверждение, что UI и инструмент. Задача из
   конфига активируется без запроса (оператор правит файл сам), но при старте
   пишется предупреждение в лог, а в UI задача видна как конфиг-задача.
5. **Наблюдаемость**: /dsh-cron/metrics отдаёт текст формата Prometheus без
   новых зависимостей; счётчики не раскрывают промпты, вывод и содержимое задач.

## Рассмотренные альтернативы

- **Конфиг только засеивает, дальше владелец — UI.**
  - Плюсы: проще, нет конфликтов.
  - Минусы: удалённая из конфига задача продолжает работать; правка конфига
    ничего не меняет; расхождение «в конфиге нет, а оно запускается».
  - Почему не выбран: production-задача, объявленная декларативно, обязана
    исчезать вместе с объявлением.
- **Полная синхронизация без метки в UI.**
  - Плюсы: меньше кода.
  - Минусы: правка такой задачи в UI молча пропадает при рестарте.
  - Почему не выбран: скрытая потеря правок оператора.
- **Токен как ссылка на credential-сервис DSH вместо настройки.**
  - Плюсы: значения нет в settings.
  - Минусы: внешний вызов нельзя проверить без настроенной записи credentials;
    для CI-сценария лишний шаг.
  - Почему не выбран: выбран маскированный ключ в настройках, как в уже
    работающем образце dsh-key-rotation; перевод на credential-ссылку возможен
    отдельной задачей.
- **Токен на все маршруты /dsh-cron/*.**
  - Плюсы: единая точка входа.
  - Минусы: один секрет открывает и настройки доставки, и всю панель.
  - Почему не выбран: избыточная поверхность под одним секретом.
- **Метрики через зависимость prom-client.**
  - Плюсы: готовый формат и гистограммы.
  - Минусы: новая production-зависимость ради нескольких счётчиков.
  - Почему не выбран: добавление зависимости — отдельная задача и согласование;
    текстовый формат Prometheus пишется вручную без библиотеки.

## Последствия

- Положительные: постоянные задачи описываются в конфиге и не требуют ручной
  работы; внешние системы управляют планировщиком по токену; гейт исполнения
  кода не обходится новыми путями; метрики есть без новых зависимостей.
- Отрицательные и риски: удаление конфиг-задач при старте необратимо для
  исчезнувших объявлений; при неверно оформленном конфиге задача может быть
  пересоздана заново. Смягчение: предупреждение в лог, метка в UI, отказ
  синхронизации при невалидной схеме.
- Изменения для эксплуатации, данных, API, безопасности: в API появляется
  префикс /dsh-cron/api/* под Bearer; в задачах появляется служебное поле
  managedBy; настройки получают ключ токена (маскируется при отдаче); в UI
  добавляется состояние «управляется конфигом».

## Проверка Решения

- Критерии успеха: задачи из конфига появляются, обновляются и удаляются при
  старте; UI-задачи не затрагиваются; внешний API без токена отвечает 401 или
  503, с токеном работает; создание код-исполняющей задачи без подтверждения
  отклоняется и на API; метрики отдаются в формате Prometheus.
- Необходимые тесты: unit на парсер и синхронизацию конфига, на проверку токена
  и сравнение постоянного времени, на формат метрик, на отказ каналов;
  integration маршрутов через мок webServer; прогон всего набора; приёмка на
  MiniPC и production-приёмка кандидата.
- Условие пересмотра: появление штатного экспортёра метрик или сервиса внешней
  авторизации в ядре DSH; либо требование хранить токен только в credentials.
