# ADR-0002: Production-приёмка кандидата до публикации

- Статус: Accepted
- Дата: 2026-09-11
- Проект: dsh-cron (правило применяется ко всем нашим DSH-плагинам)
- Связанные Gitea issues / PR: PR #125 и комментарий с доказательствами cleanup
- Заменяет / заменён ADR: нет

## Контекст

Корневой AGENTS.md требует, чтобы production получал только опубликованную
неизменяемую npm-версию. Skill dhs-plugin-release-workflow требует обратного
порядка: сначала в production принимается тот же .tgz, который затем пойдёт в
реестр, и только после чистого результата выполняется публикация, после которой
кандидат заменяется точной registry-версией. Релиз 0.2.6 был выпущен по первому
порядку: публикация, затем установка опубликованной версии и проверки. Дефект,
видимый только на реальном профиле, при таком порядке обнаружился бы уже после
публикации.

## Решение

Для 0.2.7 и далее принимается порядок из skill: разработка и merge в main, из
точного коммита main собирается .tgz кандидат, полный цикл на изолированном
тестовом сервере, тот же кандидат временно ставится в production и проходит
health/smoke/e2e и ручные критические сценарии, при чистом результате задаётся
вопрос «Публикуем релиз?», выполняется публикация npm и GitHub Release, затем
кандидат в production заменяется точной опубликованной версией и проверяется
повторно. Обе production-приёмки фиксируются в Gitea доказательствами.

Отклонение от буквы корневого AGENTS.md является осознанным и узким: временная
установка касается только проверяемого пакета, ставится штатным
package-маршрутом из собранного .tgz, не из исходников и не через file:-ссылку,
и обязательно заменяется опубликованной версией до итогового отчёта. Если
владелец потребует обратного, правило пересматривается этим же ADR.

## Рассмотренные альтернативы

- **Только опубликованная версия (порядок 0.2.6).**
  - Плюсы: строго по букве корневого AGENTS.md; проще.
  - Минусы: production-дефект обнаруживается после публикации; откат уже
    опубликованной версии дороже.
  - Почему не выбран: качество релиза важнее буквального порядка установки.
- **Отдельный тестовый профиль на production-хосте.**
  - Плюсы: боевой профиль не трогается до публикации.
  - Минусы: второй профиль со своими моделями, настройками и расписанием; риск
    разойтись с боевым окружением и получить ложную уверенность.
  - Почему не выбран: проверять надо то окружение, которое реально работает.

## Последствия

- Положительные: публикация никогда не бывает слепой; дефекты профиля ловятся до
  выпуска версии в реестр.
- Отрицательные и риски: два production-цикла установки и проверок на каждый
  релиз; краткое окно, когда в production стоит неопубликованный кандидат — на
  это время публикация обязательна к завершению либо кандидат откатывается на
  предыдущую опубликованную версию.
- Изменения для эксплуатации, безопасности, deploy: в отчёте о релизе отдельно
  фиксируются обе приёмки, кандидата и опубликованной версии.

## Проверка Решения

- Критерии успеха: в Gitea есть доказательства двух production-приёмок с версией,
  SHA и результатами health/smoke/e2e.
- Необходимые тесты и наблюдаемость: фактическая версия в профиле до и после
  замены, состояние dsh-web.service, ответы маршрутов плагина.
- Условие пересмотра: прямое указание владельца вернуться к установке только
  опубликованных версий.
