# ADR-0003: Публикационный слой для GitHub

- Статус: Accepted
- Дата: 2026-09-11
- Проект: dsh-cron (механизм применяется ко всем нашим DSH-плагинам)
- Связанные Gitea issues / PR: #128, #127; релиз 0.2.7
- Заменяет / заменён ADR: уточняет ADR-0002 в части публичного дерева

## Контекст

Правило публикации запрещает отправлять в GitHub и npm служебные файлы:
`AGENTS.md` и `index.md` безусловно, а также внутренние инструкции, планы,
findings/progress, конфиги и инфраструктурные deploy-скрипты. Обычный
зеркальный push ветки `main` отправляет весь корень репозитория, поэтому
`AGENTS.md` и `index.md` попадали в публичный репозиторий, а поле `files`
npm-пакета включало папку `docs/` целиком и затягивало планы и ADR в тарболл.

Переписывать историю, менять SHA и использовать force-push запрещено, поэтому
проблему нельзя решить «очисткой» уже опубликованных коммитов. Владелец выбрал
публикационный слой: GitHub остаётся витриной релизов, но публикуемое дерево
собирается из проверенного `main` без служебных файлов.

## Решение

1. Публичное дерево собирается из коммита `main` **без** служебных путей:
   `AGENTS.md`, `index.md`, `deploy.sh`, `publish.sh`, `docs/plans/`,
   `docs/adr/`, `docs/design/`, `.planning/`, `.worktrees/`.
2. Список исключений объявлен в `.gitattributes` через `export-ignore`, поэтому
   обезличенное дерево воспроизводимо штатным `git archive` и совпадает с тем,
   что применяет скрипт публикации.
3. `publish.sh` собирает дерево git-пламбингом (`git read-tree` → выборочное
   удаление путей из индекса → `git write-tree`), проверяет состав (нет
   служебных файлов, есть обязательные продуктовые) и создаёт публикационный
   коммит **поверх текущего публичного `main` GitHub**. Это обычный потомок,
   поэтому push fast-forward; force-режимы не используются.
4. Ветка `main` в GitHub и тег релиза указывают на публикационный коммит.
   SHA публичного дерева **не совпадает** с Gitea `main` — это осознанное
   следствие исключения служебных файлов, а не расхождение истории.
5. `AGENTS.md` и `index.md` остаются в Gitea и в DEV; в npm-пакет они не
   попадали и не попадают. Состав npm-пакета задаётся allowlist в `package.json`
   и перечисляет только продуктовые файлы.
6. Режим `bash publish.sh plan [ref]` показывает состав публичного дерева и
   валит проверку при служебном или отсутствующем обязательном файле; режим
   `publish` требует явного `DSH_CRON_PUBLISH=yes`.

## Рассмотренные альтернативы

- **Только релизы, без зеркала `main`.**
  - Плюсы: самая узкая публичная поверхность.
  - Минусы: у публичного репозитория нет актуальной ветки, поиск и просмотр
    кода работают только по тегам.
  - Почему не выбран: владелец выбрал сохранение витрины с веткой.
- **Осознанное исключение (оставить как есть).**
  - Плюсы: ничего не меняется.
  - Минусы: правило публикации остаётся нарушенным.
  - Почему не выбран: правило обязательно, а не рекомендательно.
- **Очистка истории (filter-repo, force-push).**
  - Почему не рассматривается: прямо запрещена; ломает идентичность SHA с
    Gitea и уже опубликованные ссылки.

## Последствия

- Положительные: в публичном дереве и в npm-пакете только файлы продукта;
  механизм воспроизводим и проверяем; история Gitea не переписана.
- Отрицательные и риски: SHA публичного дерева отличается от Gitea `main`,
  поэтому нельзя сверять публикацию простым равенством SHA — сверяется состав
  файлов. Уже опубликованные ранее коммиты GitHub сохраняют `AGENTS.md` и
  `index.md`; отозвать их нельзя, и это зафиксировано в #128.
- Изменения для эксплуатации, публикации и безопасности: релиз публикуется
  через `publish.sh`; тег и GitHub Release создаются от публикационного
  коммита; перед публикацией обязательна проверка состава и обезличенности.

## Проверка Решения

- Критерии успеха: `bash publish.sh plan` показывает дерево без служебных
  файлов и со всеми обязательными продуктовыми; после публикации состав ветки
  GitHub совпадает с проверенным, тег указывает на публикационный коммит.
- Необходимые тесты и наблюдаемость: проверка состава перед публикацией, поиск
  обезличенности по публичному дереву и по составу npm-пакета, сверка файлов
  ветки GitHub после push.
- Условие пересмотра: появление штатного механизма публикации в ядре DSH или
  изменение правила публикации владельцем.
