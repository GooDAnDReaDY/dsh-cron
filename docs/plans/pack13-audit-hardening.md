# План работ: Устранение замечаний независимого аудита Pack 13 (#301, #302, #303) и выпуск 0.2.47

## 1. Контекст и цели
По результатам независимого аудита коммита `903c133` (v0.2.46, PR #299, выпуск #300):
- Исправления **#242, #244, #245** подтверждены как PASS.
- Выявлены три дефекта:
  1. **#301 (High)**: Изменение истории во время сохранения создаёт дубли и смешанный снимок. В `saveAsync()` объект `data.history` ссылается на живые массивы `this.history`, а `runs.unshift(...)` в `recordRun()` во время чанковой записи со сдвигом индексов приводит к дублированию или пропуску записей.
  2. **#303 (High)**: Потоковый writer падает на native open error и может ложно resolve при end error. Вызов `removeAllListeners(\error\')` оставляет открытый `WriteStream` без обработчиков ошибок, что при ошибке открытия файла (например, `EISDIR`) приводит к `Unhandled \error\' event` и аварийному завершению процесса. При ошибке `ws.end()` callback также возможен ложный `resolve`.
  3. **#302 (Medium)**: Нестабильный retry-тест в `test/execution-engine.test.mjs` оставляет активный таймер после падения assertion и задерживает завершение тестового раннера на >5 минут из-за отсутствия `t.after()` teardown хука и жестко заданного 1300ms ожидания.
- Цель: устранить все три дефекта, пройти все тесты и preflight, повысить версию до `0.2.47` (строго z-компонент), закрыть issue #301, #302, #303, отчитаться в #300, выпустить релиз на Gitea, GitHub, npm, развернуть на MiniAI web profile и витрине VPS `goodandready.app`.

## 2. Архитектурные решения и реализация

### 2.1. Изоляция и неизменяемость снимка при сохранении (#301)
- **Файл**: `lib/store.js`.
- **Решение**:
  - В методе `saveAsync()` перед началом любой асинхронной записи формировать глубоко изолированный снимок коллекций:
    - Для `tasks`: поверхностное копирование каждого объекта задачи (`{ ...t }`), включая изолированную копию `costLedger` (`Array.isArray(t.costLedger) ? t.costLedger.slice() : t.costLedger`).
    - Для `history`: для каждого `taskId` создавать отдельную неизменяемую копию массива запусков (`Array.isArray(runs) ? runs.slice() : runs`).
    - Для `settings`: копия объекта настроек (`{ ...this.settings }`).
  - В методе `recordRun(id, runInfo)`:
    - При добавлении нового запуска использовать copy-on-write подход: создавать новый массив `[newRun, ...prevRuns]`, не мутируя предшествующий массив на месте, и сохранять его в `this.history.set(id, runs)`.
    - Это гарантирует, что даже если внешняя ссылка на массив запусков была получена до `recordRun`, она никогда не изменится.

### 2.2. Канонический жизненный цикл потока и обработка ошибок (#303)
- **Файл**: `lib/store.js`.
- **Решение**:
  - Использовать стандартный `node:stream/promises` (`pipeline`) с асинхронным генератором `generateStoreChunks(data, version, isCanceled)` и `AbortController` для контролируемой отмены.
  - `pipeline(generator, ws, { signal })`:
    - Автоматически управляет backpressure и потоковыми буферами без ручной возни с listener `drain`.
    - Корректно слушает `error`, `finish`, `close` в течение всего жизненного цикла `WriteStream`.
    - При любой нативной ошибке открытия файла (`EISDIR`, `EACCES` и др.) или ошибке записи/закрытия немедленно реджектит возвращаемый промис и корректно уничтожает поток (`ws.destroy()`), предотвращая возникновение `Unhandled \error\' event`.
    - Исключает ложный `resolve()`: промис разрешается строго после успешного завершения записи и закрытия файлового дескриптора.
    - При отмене по новой версии или синхронному сохранению контроллер отмены вызывает `abort()`, и `pipeline` безопасно прерывает запись, удаляет временный файл и не оставляет повисших дескрипторов.

### 2.3. Изоляция и надёжность retry-теста (#302)
- **Файл**: `test/execution-engine.test.mjs`.
- **Решение**:
  - В функции `makeEnv(t, options)` регистрировать очистку через `t.after(() => { try { scheduler.stopAll(); } catch {} ... })`. Это гарантирует остановку всех интервалов и таймеров планировщика даже при падении любых `assert` внутри теста.
  - В подтесте `#18`:
    - Использовать меньший таймаут бэкоффа (`retryBackoffMs: 150` или `200`) для ускорения прогона.
    - Заменить жесткий `setTimeout(1300)` на адаптивное ожидание выполнения с ограничением по времени (polling каждые 20 мс до таймаута 3000 мс).
    - Гарантировать завершение теста без зависаний процесса при любых исходах.
