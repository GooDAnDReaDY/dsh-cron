## Цель блока

Сделать планировщик пригодным для эксплуатации: объявлять постоянные задачи
декларативно в конфиге профиля, управлять задачами из внешних систем по токену,
снимать метрики для мониторинга, не терять опечатки в каналах доставки и
починить штатную проверку установки.

## DoR (Definition of Ready)

- **Измеримый результат**: 1) задачи из config.jobs создаются, обновляются и
  удаляются при старте профиля, помечены как управляемые конфигом и защищены от
  правки в UI; 2) внешний префикс /dsh-cron/api/* отвечает только по Bearer-токену
  из настроек и умеет список, создание, удаление и принудительный запуск; 3) на
  /dsh-cron/metrics отдаётся текст формата Prometheus; 4) неизвестный
  идентификатор канала даёт 400 со списком, а не молчаливое выбрасывание;
  5) deploy.sh выполняет аутентифицированную проверку после установки;
  6) parseScheduleExpression и scheduleTask разбиты на читаемые функции без
  изменения поведения.
- **Границы**: только dsh-cron. Чужие плагины, профиль web и production-настройки
  не трогаем. Новых зависимостей нет: метрики пишутся вручную в текстовом формате
  Prometheus, потому что в профиле нет prom-client, а добавление зависимости —
  отдельная задача и отдельное согласование.
- **Blast radius**: lib/index.js (маршруты, схема конфига, инструменты),
  lib/scheduler.js (синхронизация конфига, счётчики метрик, разбивка),
  lib/api.js (валидация каналов, внешние маршруты), lib/client.js (метка
  управляемой задачи, подсказка про токен), deploy.sh, документация, тесты.
- **Риски**: 1) конфиг-задачи, исполняющие код: оператор правит файл сам, но факт
  появления такой задачи обязан быть виден в логе и в UI; 2) удаление
  конфиг-задач при старте может выглядеть как потеря данных — решение владельца:
  конфиг владелец, но UI-задачи не затрагиваются; 3) внешний API расширяет
  поверхность атаки — гейт подтверждения для код-исполняющих типов сохраняется,
  сравнение токена постоянное по времени; 4) метрики не должны раскрывать промпты,
  вывод и содержимое задач — только счётчики и длительности.
- **План проверки**: unit-тесты на каждый модуль (валидация каналов, парсер
  конфига и синхронизация, токен и его сравнение, формат метрик, разбитые
  функции); integration-тесты маршрутов через мок webServer; прогон всего набора;
  полный цикл на изолированном тестовом сервере; затем production-приёмка
  кандидата, публикация и повторная приёмка уже опубликованной версии.

## Reuse-first

- Поиск по установленным плагинам профиля web: prom-client отсутствует, готового
  экспортёра метрик нет. Значит, метрики — свой минимальный текстовый рендер без
  зависимости.
- Внешний API: в проекте уже есть рабочий образец токен-авторизации —
  dsh-key-rotation/lib/routes-ops.js (Bearer из Config, 503 при незаданном токене,
  401 при несовпадении). Берём ту же форму и добавляем сравнение постоянного
  времени; концепцию «локальные маршруты остаются локальными, внешние живут под
  токеном» берём оттуда же (isTrustedBridgeRequest, проверка loopback).
- Декларативные задачи: готового образца config.jobs в профиле нет; схема
  объявляется в Config плагина, синхронизация — свой код поверх существующего store.
- Разбивка #97: продолжение уже принятого подхода (lib/api.js, разбитый путь
  запуска), новых инструментов не вводим.

## Решения владельца (2026-09-11)

1. **config.jobs — конфиг владелец.** Задачи из конфига получают метку
   managedBy: config; при старте создаются, обновляются, исчезнувшие удаляются;
   в UI они помечены и защищены от правки; обычные задачи не затрагиваются.
2. **Токен внешнего API — настройка плагина** (маскированный ключ, как botToken),
   проверка только на новом префиксе /dsh-cron/api/*; существующие маршруты
   панели остаются локальными.
3. **Гейт код-исполняющих задач — на обе поверхности.** Внешний API требует то же
   подтверждение, что UI и инструмент; задача из конфига активируется, но при
   старте пишется заметное предупреждение, а в UI она помечена как конфиг-задача.
4. **Порядок production-приёмки.** Сначала в production ставится тот же .tgz
   кандидат, что пойдёт в реестр, выполняется полная проверка, и только после
   чистого результата задаётся вопрос о публикации; после публикации кандидат
   заменяется точной registry-версией и проверяется повторно.
